## 1. 判据（以后不用逐个问）

| 维度 | 判据 | 结果 |
|---|---|---|
| **内核** | 是不是所有模块都要遵守的运行时约束？ | 是 → 常驻，不做开关、不外置服务 |
| **模块** | 能否用自己的表 + API 前缀 + 菜单圈住，关掉后别人不受影响？ | 是 → 可插拔，运行期开关 |
| **版本** | 这一版给客户开哪些模块？ | 模块的组合快照，不是功能、不是 git 分支 |
| **独立产品** | **能不能单独卖给一个客户、他不买主产品也能用？** | 是 → 独立产品，独立库与发布节奏 |
| **不属于以上** | 打包策略、演进阶段、交付形态 | 不占分类，避免混淆 |

两条硬规则：

1. **横切关注点永不独立成产品，也不外置成服务。** 隔离、鉴权、审计必须在每次调用时本地、同步、fail-fast 生效；认证可以外置成 IdP，隔离不行。
2. **抽象在内核，实现在模块。** i18n 框架 / StorageService / 消息发送接口 / 调度框架常驻；语言包、具体 Provider、通道实现、具体任务后置。

- [ ] 所有业务表**含关联表**有 `tenant_id`，唯一索引以它最左；由 CI 扫 `schema.yaml` 自动校验，不靠人工。

### 3.1 SaaS 关闭态的运行约定（首发形态）

> 前提：A5 租户地基常驻，`lx.module.saas.enabled=false`，不建 `sys_tenant` / 套餐表（`06:57`）。

| 链路 | 关闭态行为 | 影响 |
|---|---|---|
| 请求入口 | `TenantFilter` 恒写 `tenantId=0` | 无感 |
| SQL | 租户插件拼 `tenant_id = 0` | 优化器消掉常量条件，几乎零开销；**真实代码路径被天天执行** |
| 表与索引 | 每行多 8 字节，唯一键 / 联合索引最左含 `tenant_id` | 1 亿行约 800MB 量级，可忽略 |
| 缓存 / 文件 | Key 带 `:0:`，路径前缀 `0/` | 命名冗余；后期刷真实租户 ID 时，文件物理路径要有映射或迁移方案 |
| 定时任务 / 异步 / MQ | 租户列表恒为 `[0]` | 等价原逻辑；**必须走 `TenantProvider`，禁止查 `sys_tenant`** |
| 租户表 / 接口 / 菜单 | 不创建、不加载、不返回 | 符合 `README:137` |
| 越权拦截 | 无跨租户可越，规则空跑 | 必须靠「伪造 `tenant_id=1` 必须 403」用例保活 |

**必须修正 `06:59`**：原文写「租户插件先注册但空实现（不拼条件）」，这是错的。空实现意味着单租户期所有 SQL 都不带租户条件，等打开 SaaS 换成真实实现时，多表 JOIN、子查询、自定义 Mapper、count、批量更新、逻辑删除里的漏拼会集中爆发 —— 等于「第一次上线才第一次测试」。**正解是关闭态就拼常量 `tenant_id = 0`，走完整路径，打开开关只是把常量换成变量。**

关闭态必须守的 6 条：

1. 插件拼常量 `0`，不是空实现；`DEFAULT 0` 改为强制注入，缺失即报错（否则会养成「不写也没事」的编码习惯）。
2. `TenantProvider` 接口 + 常量实现 `[0]`；业务代码零直接查租户表。否则 `06:57` 不建表会直接导致启动失败；`05:1013`「默认套餐初始化」与 `06:57`「不建套餐表」的冲突也要在这里解掉。
3. 关闭态契约测试进 CI：接口 404、Bean 不加载、迁移跳过、`module_code='saas'` 菜单不返回、权限缓存不含 SaaS 权限码（`01:352` 的 30 分钟缓存要一并清）。
4. 保留越权用例：伪造 `tenant_id=1` 的请求必须 403，证明拦截链路活着。
5. CI 静态检查新增表含 `tenant_id`、唯一键含 `tenant_id`、缓存 Key / 文件前缀 / 异步传播带租户。
6. 导出与备份数据带 `tenant_id=0`；多私有化实例各自都是 0，合并时必然撞车，需单列方案（见 `10` 待修）。

**打开开关那一刻**（做到上述 6 条时）：① 迁移租户 / 套餐 / 授权表 → ② 替换 `TenantProvider` 与解析器实现（域名 / 登录租户码）→ ③ 插件常量 `0` 换成真实 `tenantId` → ④ 存量数据归属、文件路径映射、缓存 Key 灰度切换。没做到，则这一步等于全量回归 + 数据清洗。

### 3.2 多租户登录链路：不新增认证表

租户不是第三类账号主体，而是账号的一个**维度**。加租户后认证表不变，只是链路里多两步校验：

| 步骤 | 关闭态 | 开启 SaaS 后 |
|---|---|---|
| 解析租户 | 恒为 `0` | 域名 / 登录 `tenantCode` / Token / AppKey（`10:135-143`） |
| 校验租户 | 跳过 | `sys_tenant.status`、有效期、套餐模块授权 |
| 查用户 | `sys_user` + 数据范围 | 同一张表，条件加 `tenant_id = ?`（插件自动注入） |
| 权限 | `sys_role` / `sys_menu` | 不变，再与套餐模块求交 |
| 签发 Token | 会话写 `0` | 会话写 `tenantId`，后续请求不再查表 |

新增的是**租户管理表**（`sys_tenant` / `sys_tenant_module` / `sys_tenant_domain` / 套餐 / 配额），不是登录表；会员侧 `mem_*` 同理。

必须拍板的两件事：

1. 唯一键从 `uk(username)` 改为 `(tenant_id, username)` —— 「不同租户能否有同名用户」是产品决策，不是技术活。
2. 登录接口的防枚举：`tenantCode` 不存在与密码错误必须返回**同一错误码且耗时同档**，否则可枚举租户列表。

平台运营 / 超级管理员的跨租户查询走独立入口（`@CrossTenant` + 强制审计，`10:206`），不要混进普通登录链路；租户边界永远是硬条件，数据范围 5 档（`04:92-99`）是在租户内再做二次过滤。

### 3.3 隔离模式选型：默认共享表，独立库作逃逸口

> 结论：**分库/分表不是「比 `tenant_id` 更好」，是另一种权衡**。买的是物理隔离与合规，卖掉的是跨租户查询、迁移运维与多库兼容的确定性。

| 模式 | 租户内查询 | 跨租户查询 | 迁移与运维 | 结论 |
|---|---|---|---|---|
| 共享库共享表 + `tenant_id` | 正常 | 正常 | 一套 DDL、一次迁移 | **默认，覆盖绝大多数租户** |
| 每租户一张表（分表） | SQL 层被破坏 | `UNION` N 表，分页排序几乎不可行 | 100+ 表 × N 租户，版本易漂移 | **不要做** |
| 共享库独立 Schema | 切 `search_path` / `use db` | 仍需 `UNION` | 逐 schema 跑迁移；达梦/金仓语义与 MySQL/PG 不同 | 不推荐 |
| 独立库（分库） | 完全正常 | 需异步汇总通路 | 每库一套 Flyway、连接池、备份、监控 | **仅 VIP / 合规客户** |

**分表是三种里最差的**：隔离强度不如分库，复杂度一点没少。动态表名会让 MyBatis 租户插件失效（插件是加 `where` 条件，不是换表名）、Mapper XML 与代码生成器要参数化表名（表名不能占位符，只能白名单拼接，有注入风险）、关联表分不分都会形成组合爆炸、唯一键与字典等共享数据还得单独放。

**「查询不好用」要拆开看**：

- 租户内查询（业务量 90%+）：**分库下完全好用**，就是一个普通单库，SQL 不用改。
- 真正难的只有平台运营那 10%：跨租户看板、用量统计、全局搜索。
- 解法是**异步汇总到平台库**（用量 / 报表走事件或 ETL 落库），而不是为了这 10% 放弃物理隔离，更不要做实时跨库 JOIN。规划 `10:332` `saas_usage`、`10:354` 平台仪表盘目前没有汇总源，`10:126`「跨租户查询走主库」在数据已迁出后不成立，这条通路必须补。

**为什么现在不该全平台改分库**：

1. 与四库兼容相乘：MySQL / PG / 达梦 / 金仓的 schema / database 语义、连接串、DDL 各异，`14` 的方言 SPI 只处理 SQL 方言，不处理数据源路由 → 4 × 3 组合，CI 测不完。
2. 与 Flyway 冲突叠加：`06:334` 按模块分 history vs `05:996`/`14:286` 按厂商分 history，再加「按租户分」变三维。
3. 首发单租户、私有化客户一台内网服务器（`13:155`），为一个尚不存在的多租户场景先付全套成本。
4. 事务内不允许切租户、异步按租户分批、连接数膨胀、新建租户要建库 + 全量迁移 + 初始化失败重试幂等（`13:246` 只列了验收项，无设计）。

**选了分库也不能省 `tenant_id`**：它是逻辑主线，物理隔离只是实现之一。混合模式下代码统一走 `TenantContext`，由路由层决定「拼条件」还是「切数据源」；平台库、日志、缓存、文件、消息、审计仍按 `tenant_id` 组织。A5 地基一点没少。

**真正该做分库的触发条件**（满足任一，按租户单独开启，不改默认）：合规硬要求（数据不出域、等保、政务/金融）；单租户数据量或流量影响他人；客户要求独立备份 / 恢复 / 导出 / 升级窗口；要求故障域隔离。

落地方式：保留 `10:116` `TenantDataSourceRouter`，默认返回主库；仅 `sys_tenant.isolation_mode=3` 的租户路由到独立数据源，共享表租户仍走 `tenant_id` 条件。

### 3.4 租户插件的能力边界：框架处处都是 `tenant_id`

常见误解：「隔离交给 MyBatis-Plus 租户插件自动拼条件，基础框架就不用管 `tenant_id` 了」。

准确说法：**业务 Service 不手写 `tenant_id`（这是对的，`README:238` 的目标），但基础框架处处都要有它。** 插件只是框架里负责 SQL 的那一个拦截器，不是框架的替代品。`01:324-342` 自己画了六个出口，插件只占一个：

| 出口 | 谁负责 | 漏了会怎样 |
|---|---|---|
| MyBatis 租户插件（单表 CRUD） | 插件自动 | — |
| 缓存 Key 前缀 | 框架统一 Key 生成器 | A/B 租户同 `userId` 串数据；`01:352` 已漏 |
| 对象存储 / 文件路径前缀 | 框架 `StorageService` | 跨租户读到别人文件 |
| 异步线程 `TaskDecorator` | 框架上下文传播 | ThreadLocal 丢失，SQL 拿不到租户或落到 `0` |
| 定时任务 / MQ Header | 框架逐租户设置 | 任务跑错租户或串数据 |
| Token / 会话与权限缓存 | 框架认证层 | 登录后身份不带租户，越权 |
| DDL / 唯一索引 / schema 模型 | 框架元数据层 | `05:379-391` 关联表漏列；唯一键语义错 |
| 导出 / 报表 / 迁移脚本 / 原生 SQL | 框架治理 + CI 检查 | 绕过插件直接泄露 |

插件本身还**依赖**框架提供：`TenantContextHolder` 读值（`01:189` 放在 `lx-common-core`）、`ignoreTable` 白名单配置、异步与定时任务的上下文传播、开关与 fail-fast 策略。说「框架不需要」等于说「插件不需要输入」。

另一个盲区：**不是所有 SQL 都过插件** —— 手写 Mapper XML、多表 JOIN、子查询、`count`、批量更新、逻辑删除、Flyway 脚本、数据初始化脚本，都要靠插件配置覆盖或 CI 静态检查兜住。

**按「插件搞定」的理解去做，最可能的结果是：SQL 隔离对了，缓存 / 文件 / 异步全漏，而且单租户期这些值全等于 `0`，测也测不出来。** 这正是 3.1 要求关闭态就拼常量 `0`、并保留「伪造 `tenant_id=1` 必须 403」用例的原因。

一句话划分：**业务代码不写 `tenant_id`，框架代码处处是 `tenant_id`。**

## 4. 模块准入与骨架契约

准入 4 条，**全满足才准做开关**：

1. 有独立表前缀与独立 Flyway 目录；
2. 关闭后别处不 join 它的表、不注入它的 Bean、不留下悬空引用；
3. 有独立 API 前缀和 `module_code` 菜单；
4. CI 能跑「开 / 关」两种启动。

骨架：表前缀 → `db/migration/{vendor}/{module}/` → `/api/{端}/{module}/**` → 菜单 `module_code` → 依赖方向只向下（模块 → `api` 包 / 领域事件）→ 关闭态契约测试。

**开关收敛建议**：`06:28` 的三层求交（构建期 AND 运行期 AND 租户期）叠加模块数与 Flyway 双维目录，测试矩阵是组合级的。首发只保留**运行期开关 + 条件装配**，构建期裁剪与租户期套餐后置。

## 5. 独立产品的集成约定

- 把认证 / 权限 / 租户上下文 / 文件 / i18n / 消息 / 工作流 / OpenAPI 下沉为 `lx-platform`（BOM / SDK 形式），必要时独立部署认证中心。
- 内容平台、商城、ERP 各自独立仓库、独立库、独立发布节奏，经 `lx-open` + SSO 集成，共享登录态与 `TenantContext`。
- 这正是 `01:483` ADR-01「达到指标再拆」的触发场景，而不是提前塞进同一 jar。
- **动手前先定主数据归属**：商品 / 库存 / 订单归商城还是 ERP；不定归属，两套 SKU 必然对不上账。
- 商城多商户是「租户内再分账」，与 `10:99-103` 的三层隔离不是同一层级，不要塞进现有 `TenantContext` 语义。

### 5.1 为什么现在不做微服务 + K8s

结论：**不合理，`README:31` / `01:483` ADR-01 的判断不要推翻。** 更关键的是，微服务恰好会放大当前最脆弱的两处问题。

| 理由 | 依据 |
|---|---|
| 规模不匹配 | 2~3 人 + AI、6~8 个月；`13:99-105` 的 DevOps 只有 0.5~1 人兼职 |
| 隔离逻辑散落 | 租户是数据层横切约束，拆服务后每个服务各实现一遍 `tenant_id` / 上下文 / 越权，漏一处即泄露 |
| 事务边界被打碎 | `01:44` 明确不引分布式事务；CMS 发布（`07:228-234`）、工作流起流程（`08:264-266`）本就脆弱，拆开后要上 Saga / 补偿 |
| 测试矩阵再乘一维 | 三层开关 × 模块 × 四厂商 DDL，再加服务拓扑，CI 无法收敛 |
| 客户现场不匹配 | `13:155` v1.0 面向私有化 / 信创客户，常见是一台内网服务器、无 Docker / K8s 权限；`java -jar` + Nginx 是最大公约数 |
| 两者是两件事 | 单体也能上 K8s，拆服务也能先跑 Compose；不要把两个决策绑定 |

**担心单体变胖时的正确解法**：Maven 多模块 + 严格依赖方向（`01:119-122`）、关闭态契约测试、把无状态且资源特征不同的部分（图片处理、静态化、搜索索引）做成**独立进程 / 独立任务**并由 Outbox 驱动 —— 保留单进程事务，同时给将来拆分留缝。

**拆分触发指标**（满足 2~3 条再动，逐块拆，不一步到位）：

- 团队 ≥ 3 个独立小队，需要互不阻塞的发布节奏；
- 某模块资源特征明显不同（图片 CPU 密集 / ES 内存密集），需独立扩容；
- 单模块负载把单机打满，且垂直扩容不够；
- 出现第二个独立产品（商城 / ERP）需独立部署 —— 这是 `01:483` 最正当的触发点；
- 有专职运维 / SRE，且客户环境确实提供 K8s。

先拆边界最清、无状态、无强事务依赖的块（文件 / 图片处理），不要先动权限、租户、内容发布。

### 5.2 澄清：「单独开启」与「单独启动项目」是两件事

目标形态：先做完整版后台基座，CMS / 多租户 / 工作流 / ERP / 商城 / 公众号 / 支付等各自单独开启；多租户甚至单独启动一个关联项目。

**这两个动词不能混用**：

| 说法 | 实际含义 | 适用对象 |
|---|---|---|
| 单独开启 | 同一进程内的运行期开关（Bean / API / 迁移 / 菜单 / 前端路由不加载） | B 类模块 |
| 单独启动项目 | 独立进程、独立库、独立发布节奏，跨进程集成 | C 类独立产品、平台运营控制台 |

按第 2 节分类重新归位：

- 后台基座 + 内核 = **A**，必装；
- CMS、工作流、会员、文件增强、搜索、开放平台、基础支付、i18n 内容 = **B**，可单独开启；
- 公众号 = **渠道适配器**，建议并入 `message` / `open` 的 Provider，不单列业务模块（否则开了没内容可发）；
- ERP、商城 = **C，独立产品**，不要当模块塞进同一后台；
- 多租户 = **A5 地基 + B 类管理功能**，不是独立产品。

**多租户能不能单独起一个关联项目？一半可以**：

- **管理侧可以**：超管、租户开通、套餐计费、跨租户看板、初始化调度，做成独立部署的运营控制台，安全等级与发布节奏都不同。
- **隔离机制不可以**：每个业务应用仍须自带 `TenantContext` + 本地租户插件 + 缓存 / 文件 / 异步前缀。运营控制台只负责**下发租户档案**，各应用本地缓存并使用，即「**管理集中，执行本地**」。若让业务请求每次 RPC 去问「我是谁、能看什么」，性能、可用性、fail-fast 全崩，且 3.4 的框架责任一条都省不掉。

**根本矛盾**：模块能否单独开启，取决于基座是否提供了它需要的公共契约。CMS 要内容模型与发布状态机；ERP / 商城要多组织、账套、金额精度、单据状态机、字段级权限。要同时满足，基座要么膨胀成「什么都有」，要么各模块自己造轮子 —— 与「先做一个干净完整版后台」冲突。这也是 ERP / 商城必须独立成产品的原因。

**建议的落地顺序**：

1. `lx-boot` 基座 + 内核 + 2~3 个 B 模块（CMS / 文件 / i18n），单租户、jar 部署；
2. 先把「关闭态启动」契约测试跑通，再加工作流 / 会员 / 公众号 / 支付 —— **先证明开关收得住，再增加模块数**；
3. 有真实 SaaS 需求时，把运营控制台独立部署，各应用本地上下文保持常驻；
4. ERP / 商城作为独立产品立项，复用内核（BOM / SDK + SSO + `lx-open`）。

**规模提醒**：B 模块从 14 个涨到约 20 个，测试矩阵 2^N；再叠加 ERP / 商城两个产品，`13:145` 的 53~66 人月估算已不成立，需重算范围与排期。

### 5.3 模块开关 vs 独立项目：判据与拆分顺序

**结论：默认模块开关，满足强条件才独立项目。两者不是对立，而是“代码边界”与“交付边界”的区别。**

| 判据 | 模块开关（同进程） | 独立项目（独立进程 / 库 / 发布） |
|---|---|---|
| 能否单独卖给一个客户 | 否，必须依附主产品 | 是，客户不买主产品也能用 |
| 数据是否必须独立 | 共享库、共享表即可 | 合规 / 大客户要求独立库 |
| 资源特征 | 与主应用相近 | 图片处理、搜索索引、报表等 CPU / IO 特征差异大 |
| 发布节奏 | 跟主产品一起发 | 独立团队、独立版本、独立灰度 |
| 故障域 | 可接受一起挂 | 必须隔离，不能被主应用拖死 |
| 团队规模 | 2~3 人 + AI | 有独立小队与运维 |

**判定规则：**

1. 六条里没有一条成立 → **模块开关**。
2. “能否单独卖”成立 → **独立产品**，不要塞进同一后台。
3. 只有“资源特征 / 故障域”成立 → **先拆无状态 worker**（图片处理、静态化、搜索索引），不动业务主库。
4. 只有“独立发布 / 团队”成立 → **独立部署单元**（如平台运营控制台），复用同一内核。
5. 拿不准 → **先做模块，设拆出阈值**；先模块后独立，比先独立后合并便宜得多。

**凌霄的归位：**

| 能力 | 形态 | 理由 |
|---|---|---|
| system / file / i18n / message / job | 模块（必装） | 所有业务共用，拆出去只会增加 RPC |
| CMS / member / workflow / search / 基础支付 | 模块（运行期开关） | 同一内容域，共享用户、文件、权限、发布链路 |
| 平台运营控制台（SaaS 超管 / 套餐 / 计费 / 跨租户看板） | 独立部署单元 | 安全等级、发布节奏、跨租户查询都不同 |
| 图片处理 / 静态化 / 搜索索引 worker | 可独立进程（后期） | 资源特征不同，用 Outbox 驱动，不共享事务 |
| ERP / 商城 | 独立产品 | 能单独卖，主数据与状态机与内容平台冲突 |
| 多租户隔离机制 | 内核能力，不是项目 | 必须在每次数据访问时本地、同步、fail-fast 生效 |

**拆分顺序（不要反过来）：**

1. 先证明模块开关收得住：关闭态能启动、接口 404、Bean 不加载、迁移跳过，进 CI。
2. 再拆无状态 worker：图片、静态化、索引；主库事务不变。
3. 再拆运营控制台：只下发租户档案，业务应用本地执行隔离。
4. 最后拆独立产品：ERP / 商城复用内核 BOM / SDK + SSO + `lx-open`。

**两个反模式：**

- 用独立项目逃避模块化：边界没定清就拆进程，结果每个项目复制一套权限、文件、i18n、消息，联调成本翻倍。
- 用模块开关假装产品隔离：能单独卖的 ERP / 商城塞进同一 jar，基座被交易概念污染，最后既不像内容平台也不像 ERP。

**v1.0 的落地口径（2026-11-11 定稿）：** 一个 `lx-boot`（**平台后台 + 文件中心**），只做**运行期开关 + 条件装配**；构建期 Profile 与租户期套餐后置。**v1.0 不建 CMS / 会员 / 门户**，它们按 v1.1~v1.3 以模块嵌入，见 `20-cms-embed-plan.md`。不要一开始就拆多项目，也不要一次铺 20 个模块。
